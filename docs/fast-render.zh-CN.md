# 把视频输出从 15 分钟缩短到 1 分 41 秒

<sub>2026-10-04　作者：欸不是　实现与撰写：Claude Opus 5.5（Claude Code）</sub>

《人类大历史》是一部 149 秒、全部用代码画出来的短片。原本输出一次要 15 分半，现在只要 1 分 41 秒，快了 9 倍多，画面肉眼看不出差别。

这篇文章记录是怎么做到的。重点不在某个技巧，而在方法：**先测，找到真正的瓶颈，再动手。** 这次一共找到两个瓶颈，第二个藏得很深，靠猜是猜不到的。

| | 原本 | 现在 |
|---|---|---|
| 整片 1080p30（4470 帧，每帧 4 个子帧做动态模糊） | 932 秒 | **101 秒** |
| 整片 4K60（8940 帧，每帧 8 个子帧） | 估计约 4 小时 | 估计 20–30 分钟 |
| 和 HeyGen 开源的 HyperFrames 比（同一段 30 秒、不做动态模糊） | — | 22 秒 对 50 秒 |

所有数字都在 Apple M3（16 GB）上实测。测试的代码就在这个项目里，可以自己重跑（见文末）。

---

## 背景：这部片怎么变成视频

这部片的画面是一个网页（`stage.html`）。它只遵守一条规则：给它任何时间 t，它就画出完全相同的一帧（`window.__seek(t)`）。输出程序 `render.mjs` 开几个 Chrome，各自负责一段，一帧一帧地画，最后交给 ffmpeg 编成视频。

为了做出真正的动态模糊，每一帧会在“快门开着”的那段时间里画 4 次，再取平均。所以 149 秒的片要画 4470 × 4 = 17,880 次。

## 第一步：先测，不要猜

一帧画面要画多久？在浏览器里实测，**大约 5 毫秒**。照这个速度，画 17,880 次只要约 90 秒，但整片输出花了 932 秒。

所以绝大部分时间不是花在“画”，而是花在“把每一帧搬出来”：旧做法每画一次就截一张 1920×1080 的图，压成 JPEG，经过浏览器的调试接口传给 Node，再写给 ffmpeg。换算下来，每张截图约 300 毫秒，是画图本身的六十倍。

## 第二步：不截图，直接交给硬件编码器

Chrome 有一套叫 WebCodecs 的功能，网页可以直接使用电脑的视频编码器。Mac 上背后就是硬件编码器（VideoToolbox）。新的做法完全在页面里完成：

```js
for (let n = a; n < b; n++) {
  for (let j = 0; j < SUB; j++) {                 // 动态模糊：快门期间画 SUB 次
    window.__seek((n + offset(j)) / FPS);
    acc.globalAlpha = 1 / (j + 1);                // 连续平均：第 j 张占 1/(j+1)
    acc.drawImage(canvas, 0, 0);
  }
  encoder.encode(new VideoFrame(accCanvas, { timestamp }));   // 硬件 H.264
}
```

编码后的数据每累积几 MB 就交回 Node，写进文件。每个 Chrome 负责的一段都从关键帧开始，所以最后可以直接首尾相接，ffmpeg 只负责封装和混入配乐，不用重新编码。

**只开一个 Chrome，速度就从每秒 0.8 帧提升到每秒 18 帧。** 开几个 Chrome 最快，也要实测（片中 60–90 秒，每帧 4 个子帧）：

| Chrome 数 | 1 | 2 | 3 | 4 | 6 |
|---|---|---|---|---|---|
| 每秒帧数 | 34 | 47 | **49** | 46 | 38 |

开超过 3 个反而变慢，因为显卡和硬件编码器被抢着用。默认就设成 3 个。

画面正确性：4470 帧一帧不差，和原本的发行版逐帧比对，平均 PSNR 44 dB（差异来自两种编码器的压缩方式不同，并排看不出来）。

**但整片仍然要 471 秒**，只快了一倍。照每帧 5 毫秒推算，应该两分钟就跑完。一定还有什么地方特别慢。

## 第三步：瓶颈藏在画面里

这次逐秒测，片子的每一秒取几帧，计算每帧要画多久。

这里有一个陷阱：浏览器的画布绘图是先排队，晚一点才交给显卡执行。如果只测 JavaScript 的执行时间，看到的是“排队”花了多久，而不是“画”花了多久。要在每次绘图之后读回一个像素（`ctx.getImageData(0, 0, 1, 1)`），强迫浏览器等显卡画完，测到的才是真正的时间。

<img src="images/fast-render-profile.zh-CN.svg" alt="每一秒的绘图时间：修正前 17 到 32 秒一帧要 200 到 500 毫秒，修正后最慢的一帧约 80 毫秒">

第 17 到 32 秒（“火”的后半到“田”），一帧要 200–500 毫秒，其他段落只要 10–30 毫秒。光这 16 秒，就占了整片绘图时间的四分之三以上。（第 108 秒那根较短的高峰，是埃菲尔铁塔镜头里的塞纳河，同样是延伸到画面外的虚线。）

这一段的 JavaScript 只要 1–3 毫秒，所以成本全在显卡那一侧。接着用排除法：把可疑的绘图函数一个一个换成什么都不做，再测一次。光晕、地面的点、帐篷、岩壁贴图、模糊滤镜都不是原因。最后找到元凶：**虚线**。

| 去掉什么 | 18 秒 | 25 秒 | 30 秒 |
|---|---|---|---|
| （原样） | 427 毫秒 | 226 毫秒 | 207 毫秒 |
| 虚线改成实线 | **11 毫秒** | **10 毫秒** | **11 毫秒** |

河流用的是会流动的虚线，而且一路延伸到地平线外很远的地方，投影到画面上可能长达几百万像素。浏览器不会先跳过画面外的部分，而是把整条路径都切成一段一段的虚线，一帧就要切几百万段。

**修法**：画虚线之前，先把投影后的折线裁到画面范围（外加一点边）里，再一段一段描，然后用 `lineDashOffset` 补回被裁掉的长度，让看得到的虚线位置和原本一样。

这里的细节要用实验确认，不能凭印象。在 Chrome 里画两条线逐像素比对，确认了三件事：

1. 偏移量要“加上”裁掉的长度（用减的话，整条虚线会错开）。
2. 一条路径断开成好几段时，每一段的虚线重新起算，不会接续。
3. 折线拐角处的长度照常累计。

另外还发现两件事：

- **`lineDashOffset` 不会自己归零。** 原本的代码画完虚线只调用 `setLineDash([])`，偏移量会残留给下一条虚线。结果片中的铁路、航线、长城的垛口，其实都沿用了河流留下来的偏移量。为了让成片不变，新的代码照样沿用。新写的代码要记得自己归零。
- **线长到约一百万像素时，浏览器本身的计算就有误差。** 原本画出来的虚线位置已经有点偏，裁过之后反而是精确的。所以河流那几帧没办法和原本逐像素相同（51–54 dB，肉眼看不出来）；其他画面都在 78 dB 以上，等于完全一样。

修完之后，每一秒取一帧、149 帧的绘图时间加总，从 7.0 秒降到 2.8 秒，**整片输出从 471 秒降到 101 秒**。

## 和 HyperFrames 比较

[HyperFrames](https://github.com/heygen-com/hyperframes) 是 HeyGen 开源的“用网页写视频”框架，GitHub 上有 5.6 万颗星，也是给 agent 用的。为了知道这次的做法放到外面有没有意义，用同一段画面做了公平比较：

- 同一份绘图代码，文明片 1:39 起的 30 秒，1080p30，共 900 帧。
- 用 HyperFrames v0.8.115 的适配方式，把 `__seek(t)` 包成它认得的时间轴。
- 两边都不做动态模糊；HyperFrames 测了默认设置和它最快的设置。

<img src="images/fast-render-bench.zh-CN.svg" alt="900 帧的总时间：HyperFrames 默认 84 秒、加硬件编码 61 秒、4 个工作进程 50 秒；本项目 22 秒，加上动态模糊 49 秒">

| 设置 | 总时间 |
|---|---|
| HyperFrames 默认（自动选 1 个工作进程） | 84 秒 |
| HyperFrames 加硬件编码（`--gpu`） | 61 秒 |
| HyperFrames 加硬件编码，4 个工作进程（最快） | 50 秒 |
| 本项目 | **22 秒** |
| 本项目，加上动态模糊（每帧画 4 次） | 49 秒 |

在这个场景下快约 2.3 倍；做了 4 倍运算量的动态模糊，速度也和 HyperFrames 不做模糊时差不多。

公平起见，也要说清楚它的优势：

- **HyperFrames 能处理网页元素**（文字、界面、视频片段）。本项目的快速做法只认画布，遇到网页元素会退回截图，速度和它差不多甚至更慢。
- **它正在变快。** 新版在 Mac 上加入了一种不截图的捕获方式（drawElementImage），只开一个工作进程时就会用上，差距正在缩小。
- **它是持续维护的完整产品**；本项目只是一部片的输出程序。

所以结论不是“它比较慢”，而是：**如果画面全部画在画布上，硬件编码这条路值得走；如果是网页排版的片，用 HyperFrames。**

附注：HyperFrames 默认会发送匿名使用统计（电脑配置与使用次数），可以用 `hyperframes telemetry disable` 或环境变量 `DO_NOT_TRACK=1` 关闭。

## 能带走的经验

1. **慢的时候先测，不要猜。** 这次的两个瓶颈（截图、虚线）都不在直觉会怀疑的地方。
2. **测显卡的时间，不能只测 JavaScript。** 画完读回一个像素，强迫同步，再计时。
3. **找到慢的段落后用排除法**，一次关掉一个绘图动作。
4. **纯画布的动画不需要截图。** WebCodecs 直接编码，省掉最大的固定成本。
5. **画面外的东西也有成本。** 尤其是虚线、阴影、模糊这类浏览器会整条处理的效果。
6. **每一个“应该一样”都要逐帧比对证明。** 这次靠逐帧比对，才发现残留偏移量和精度误差这两件事。

## 限制

- 只在 Apple M3（16 GB）上测过。其他电脑的硬件编码器、最佳的 Chrome 数量可能不同。
- 4K60 只实测了 3 秒（每秒 7.7 帧），整片时间是推算的。
- 硬件编码的文件比 x264 大一成左右，画质相当。
- 需要电脑上装有 Google Chrome。

## 自己复现

```bash
git clone https://github.com/DDChen666/civilization-film.git && cd civilization-film
npm install && pip install -r requirements.txt
python3 score.py           # 合成配乐
npm run render:sc          # 整片（快速做法会自动启用）
node render.mjs video --engine shot --html "stage.html?lang=sc" --audio audio/score.wav --out out/old.mp4   # 用旧的截图做法对照
```
